# 8Byte DevOps Assignment

A full CI/CD + infrastructure setup for a two-tier app (frontend + backend + Postgres), deployed on EKS, with monitoring, logging, and an automated deployment pipeline.

## Must Have At Start 

Before starting, you'll need:

- An AWS account with admin access (to create IAM roles, VPC, EKS, RDS)
- AWS CLI, configured (`aws configure`)
- Terraform (`brew install terraform` )
- kubectl (`brew install kubectl`)
- Helm (`brew install helm`)
- eksctl (`brew install eksctl`)
- Docker Desktop (running)
- A GitHub account, with the repo forked/cloned locally

## Setup — step by step

### 1. Bootstrap remote state (one-time)

```bash
cd terraform-bootstrap
terraform init
terraform apply
```
Creates the S3 bucket + DynamoDB table that hold Terraform's state — needed before the main config, since it points at this bucket.

### 2. Provision the infrastructure

```bash
cd ../terraform
cp terraform.tfvars.example terraform.tfvars   # set a real db_password
terraform init
terraform apply
```
Builds the VPC, subnets, EKS cluster + node group, RDS, ECR repos, and IAM roles. EKS takes ~10 minutes; RDS takes ~5-10.

### 3. Connect kubectl

```bash
aws eks update-kubeconfig --name 8byte-eks --region ap-south-1
kubectl get nodes
```
Should show 2 nodes, `Ready`.

### 4. Install the AWS Load Balancer Controller

```bash
eksctl utils associate-iam-oidc-provider --cluster 8byte-eks --region ap-south-1 --approve

eksctl create iamserviceaccount \
  --cluster=8byte-eks --namespace=kube-system --name=aws-load-balancer-controller \
  --attach-policy-arn=arn:aws:iam::<ACCOUNT_ID>:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve

helm repo add eks https://aws.github.io/eks-charts
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=8byte-eks \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set vpcId=<VPC_ID_FROM_TERRAFORM_OUTPUT>
```
This is what turns a Kubernetes `Ingress` object into a real, working ALB.

### 5. Build and push the app images

```bash
aws ecr get-login-password --region ap-south-1 | \
  docker login --username AWS --password-stdin <ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com

cd app/backend
docker build --platform linux/amd64 -t <ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com/8byte-app:latest .
docker push <ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com/8byte-app:latest

cd ../frontend
docker build --platform linux/amd64 -t <ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com/8byte-frontend:latest .
docker push <ACCOUNT_ID>.dkr.ecr.ap-south-1.amazonaws.com/8byte-frontend:latest
```

### 6. Create the DB secret and deploy

```bash
kubectl create secret generic db-credentials --from-literal=password='<your-rds-password>'
cd ../../k8s
kubectl apply -f .
```
Give it a minute or two for the ALB to provision, then:
```bash
kubectl get ingress
```
That address is your live app.

### 7. (Optional) Monitoring stack

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install monitoring prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace \
  --set grafana.adminPassword='<your-choice>'

kubectl apply -f k8s/backend-servicemonitor.yaml
kubectl apply -f k8s/grafana-ingress.yaml
```

### 8. (Optional) Centralized logging

```bash
aws eks create-addon --cluster-name 8byte-eks --addon-name amazon-cloudwatch-observability --region ap-south-1
aws iam attach-role-policy --role-name <NODE_ROLE_NAME> --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy
```

## Architecture decisions

- **EKS over plain EC2 or ECS** — chosen specifically to demonstrate the broader Kubernetes ecosystem (service discovery, RBAC, ingress controllers), even though it required the most setup.
- **Managed node groups, not Fargate** — a deliberate choice to show real EC2-backed node management (IAM roles, scaling config) rather than abstracting it away.
- **ALB provisioned via Kubernetes Ingress, not a static Terraform `aws_lb`** — the AWS Load Balancer Controller keeps target registration in sync automatically as Pods scale or restart; a static Terraform ALB can't do that. This means the ALB itself isn't Terraform-managed — a conscious tradeoff.
- **Frontend and backend are separate Deployments/Services** — only the backend ever holds database credentials; the frontend is a plain static-file server.
- **Staging and production are separate GitHub Environments** (enabling the required manual-approval gate) **but currently deploy to the same EKS cluster.** Real separation (a second cluster or namespace) is the natural next step, not built here given scope/timeline.
- **Monitoring is a hybrid**: Prometheus + Grafana for cluster/application metrics, CloudWatch (via a second Grafana data source) for RDS metrics, since RDS doesn't natively expose a Prometheus endpoint.

## Security considerations

- **Network layering** — only the ALB sits in public subnets. EKS nodes, Pods, and RDS all live in private subnets, no direct internet exposure.
- **Security group chain** — RDS only accepts connections from the EKS cluster's security group. No broad "allow from anywhere" rule on the database.
- **No hardcoded secrets** — the DB password is a Kubernetes Secret, injected as an environment variable at runtime, never committed. `terraform.tfvars` is gitignored.
- **CI/CD credentials** — a dedicated IAM user (`github-actions-ci`), separate from any personal account, used only for the pipeline. *(Known limitation: currently has `AdministratorAccess` rather than a scoped policy — a deliberate time tradeoff; production would use least-privilege + OIDC-based short-lived credentials.)*
- **Repository visibility** — public, which was required to unlock GitHub's free-tier "required reviewers" environment protection. No secrets live in the repo itself.
- **Vulnerability scanning** — `pip-audit` runs on every PR (caught and fixed 7 real CVEs during development); ECR scans every pushed image automatically.

---

## Cost optimization

- **Single NAT Gateway**, not one per AZ — roughly halves that specific cost, at the expense of slightly less redundancy.
- **Single-AZ RDS** — Multi-AZ would roughly double RDS cost for automatic failover; not needed for a demo workload.
- **Small instance sizes** — `db.t3.micro` for RDS, `t3.medium` × 2 for EKS nodes.
- **7-day RDS backup retention**, not longer, since this isn't production data.
- **CloudWatch/Grafana usage kept minimal** to stay within free-tier ingestion limits where possible.

---

## Secret management & backup strategy

- **Secret management** — the DB password is a Kubernetes Secret, created via `kubectl create secret` (never committed as plaintext YAML), injected via `valueFrom.secretKeyRef`. CI/CD's AWS credentials live in GitHub Secrets.
- **Backup strategy** — RDS automated backups, 7-day retention (`backup_retention_period = 7`), giving point-in-time recovery over that window.

## Known limitations / what I'd do differently with more time

- Staging and production share one cluster (see Architecture decisions).
- ALB access logs (request-level logging to S3) aren't enabled — a straightforward addition via `access_logs.s3.enabled`, deprioritized in favor of finishing metrics/logging.
- Application/system logs are centralized in CloudWatch but not yet surfaced inside Grafana itself.
- The CI/CD IAM user has broader permissions than strictly necessary (documented above).
- The Load Balancer Controller's IAM/OIDC setup lives outside Terraform (done via `eksctl`) — a real infra-as-code coverage gap, noted rather than hidden.
