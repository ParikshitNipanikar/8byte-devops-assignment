## Setup — step by step

### 1. Bootstrap remote state (one-time)

```bash
cd terraform-bootstrap
terraform init
terraform apply
```
Creates the S3 bucket + DynamoDB table that hold Terraform's state — needed before the main config, since it points at this bucket.

### 2. Provision the infrastructure

```bash
cd ../terraform
cp terraform.tfvars.example terraform.tfvars   # please set your real db_password here so that u can configure you postgres
terraform init
terraform apply
```
this will Builds the VPC,IGW,NAT GW,subnets,route tables,EKS cluster + node group, RDS, ECR repos, and IAM roles.
This will take around 15-20 min

### 3. Connect kubectl
Now We have connect to our eks cluster so that we configure and get live things 

```bash
aws eks update-kubeconfig --name 8byte-eks --region ap-south-1
kubectl get nodes
```
output Should contains 2 nodes, In READY state.

### 4. Install the AWS Load Balancer Controller

AS i Go with EKS architecture i have i used ALB controller as it continously checks services and guides the ALb about pods health and it is automated process so we dont need to set a target groups and worry about syncing the health of pods

```bash
eksctl utils associate-iam-oidc-provider --cluster 8byte-eks --region ap-south-1 --approve

eksctl create iamserviceaccount \
  --cluster=8byte-eks --namespace=kube-system --name=aws-load-balancer-controller \
  --attach-policy-arn=arn:aws:iam::<ACCOUNT_ID>:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve

helm repo add eks https://aws.github.io/eks-charts
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=8byte-eks \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set vpcId=<VPC_ID_FROM_TERRAFORM_OUTPUT>
```

This is what turns a Kubernetes Ingress into proper ALB.

### 8. Centralized logging

Application and system logs are centralized via the amazon-cloudwatch-observability EKS add-on — a single, AWS-managed install that bundles the CloudWatch agent and Fluent Bit together, avoiding a separate manual Helm/IAM setup for logging specifically.

```bash

aws eks create-addon --cluster-name 8byte-eks --addon-name amazon-cloudwatch-observability --region ap-south-1
aws iam attach-role-policy --role-name <NODE_ROLE_NAME> --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy


```
here we are adding cloudwatch to eks cluster and assigning iam role so that permission will get

after this go to AWS dasboard and check for CloudWatch and inside it there will be node-groups u will see like below

Logs land in three CloudWatch Log Groups:
- `/aws/containerinsights/8byte-eks/application` — application (container stdout/stderr)
- `/aws/containerinsights/8byte-eks/host` — system (node-level logs)
- `/aws/containerinsights/8byte-eks/dataplane` — Kubernetes control plane components

## Architecture decisions

1. EKS over plain EC2 or ECS :-
   chosen specifically to demonstrate the broader Kubernetes ecosystem (service discovery, RBAC, ingress controllers), even though it required the most setup.
2. ALB provisioned via Kubernetes Ingress, not a static Terraform aws_lb :-
   he AWS Load Balancer Controller keeps target registration in sync automatically as Pods scale or restart, a static Terraform ALB can't do that.
3. Frontend and backend are separate Deployments/Services:— 
   only the backend has database credentials.
4. Staging and production are separate GitHub Environments:-
   enabling the required manual-approval gate 
5. Monitoring is a hybrid: 
   Prometheus + Grafana for cluster/application metrics, CloudWatch (via a second Grafana data source) for RDS metrics, since RDS doesn't natively expose a Prometheus endpoint.

---

## Security considerations

1. Network layering:— 
   only the ALB sits in public subnets. EKS nodes, Pods, and RDS all live in private subnets, no direct internet exposure.
2. Security group chain:— 
   RDS only accepts connections from the EKS cluster's security group
3. No hardcoded secrets:— 
   the DB password is a Kubernetes Secret.
4. CI/CD credentials:— 
    Seprate IAM user github-actions-ci. also all the need secured values stored in a Github secrets.

- **Vulnerability scanning** — `pip-audit` runs on every PR (caught and fixed 7 real CVEs during development); ECR scans every pushed image automatically.

## Cost optimization

- **Single NAT Gateway**, not one per AZ — roughly halves that specific cost, at the expense of slightly less redundancy.
- **Single-AZ RDS** — Multi-AZ would roughly double RDS cost for automatic failover; not needed for a demo workload.
- **Small instance sizes** — `db.t3.micro` for RDS, `t3.medium` × 2 for EKS nodes.
- **7-day RDS backup retention**, not longer, since this isn't production data.
- **CloudWatch/Grafana usage kept minimal** to stay within free-tier ingestion limits where possible.

---

## Secret management & backup strategy

- **Secret management** — the DB password is a Kubernetes Secret, created via `kubectl create secret` (never committed as plaintext YAML), injected via `valueFrom.secretKeyRef`. CI/CD's AWS credentials live in GitHub Secrets.
- **Backup strategy** — RDS automated backups, 7-day retention (`backup_retention_period = 7`), giving point-in-time recovery over that window.

## Known limitations / what I'd do differently with more time

- Staging and production share one cluster (see Architecture decisions).
- ALB access logs (request-level logging to S3) aren't enabled — a straightforward addition via `access_logs.s3.enabled`, deprioritized in favor of finishing metrics/logging.
- Application/system logs are centralized in CloudWatch but not yet surfaced inside Grafana itself.
- The CI/CD IAM user has broader permissions than strictly necessary (documented above).
- The Load Balancer Controller's IAM/OIDC setup lives outside Terraform (done via `eksctl`) — a real infra-as-code coverage gap, noted rather than hidden.
